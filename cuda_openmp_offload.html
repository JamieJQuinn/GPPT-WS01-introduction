What is a GPU?

A hardware view

  • CPU cores -> streaming multiprocessors
  • Each SM executes ~4 warps
  • Each warp executes 32 threads in lockstep
  • Threads execute kernels

1 warp instruction is analogous to a CPU vector instruction

  • CPU core: 2 AVX-512 (2x8 FP64)
  • SM: 4 executing warps (4x16 FP64)

GPUs are (kind of) wide vector machines!

But GPUs are SIMT, not SIMD.

SIMT vs SIMD

Single Instruction Multiple Data

  • vector lane 0 accesses index 0
  • vector lane 1 accesses index 1
  • …
  • data pre-packed into vectors before execution

Single Instruction Multiple Threads

  • thread i calculates its own data index

Difference is small. GPU kernels are slightly more flexible.

The memory hierarchy

  • Host memory - O(1 TB)
  • GPU memory - O(100 GB)
  • L2 cache - O(100 MB)
  • Shared memory / L1 cache O(10 MB)
  • Registers O(1e4 registers) per SM

What is a GPU?

A software view

                    ┌───────────────────────────────┐
                    │┌──────┐ ┌──────┐ ┌──────┐     │
                    ││tx128 │ │tx128 │ │tx128 │     │
                    ││      │ │      │ │      │ ... │
                    │└──────┘ └──────┘ └──────┘     │
                    │ Block0   Block1   Block2      │
                    └───────────────────────────────┘
                                  Grid
  • A kernel launch creates a grid of blocks
  • Each block is made of a set number of threads
  • Each thread executes the kernel body

The blocks are split into warps!

Keep in mind

  • Thread-level (one kernel body per thread)
  • Block-level (relevant for __syncthreads())
  • Warp-level (this is the hardware’s view!)

The warp scheduler

Each SM has 4 schedulers, each with 4+ active warp slots:

                    ┌────────────┐        
                    │┌─┐┌─┐┌─┐┌─┐│Active  
                    │└─┘└─┘└┬┘└▲┘│warps   
                    │       │  │ │        
                    ┼───────┼──┼─┼        
                    │┌─┐┌─┐┌▼┐┌┴┐│Resident
                    │└─┘└─┘└─┘└─┘│warps
                    └────────────┘        
                         SM0

When a warp stalls (e.g. from a memory access) the scheduler can switch within a clock cycle. This is key to general GPU performance.

Occupancy is the ratio of active / maximum warps. Measures ability of GPU to hide latency.

High-latency instructions & memory access limit actual occupancy.

Limited resources like registers and shared memory limit theoretical occupancy.

H100 SMs have 4 schedulers with 64 active warps!

I.e. 2048 active threads and 128 currently executing.

Ideal is:

Why?

PCIe 5: ~60 GB/s

GPU RAM: 2000+ GB/s

How?

Wait

Latest AMD & Nvidia cards have O(200) GB / GPU.

Use streaming

Stream data to/from GPU as required. Key optimisation is interleaving compute & data transfers.

Go multi-GPU

Split problem across many GPUs. Key technologies include MPI, collective libs, SHMEM libs.

How do GPUs do branching?

Each warp executes all instructions but masks the output.

__global__ void branch(float *out, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if(i >= n) return;

  if(i%2 == 0) {
    out[i] = 1.0;    // runs with mask 01010101
  } else {
    out[i] = sin(i); // runs with mask 10101010
  }
}

Branches take as long as the sum of their runtimes.

How do GPUs access memory?

CPU & GPU memory hardware load data in cache lines (64-128 bytes).

On GPU, 1 warp (32 threads) should access contiguously for ideal memory performance.

Uncoalesced case:

__global__ void my_kernel(float* x) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  x[32*i] += 1;
}
0 -> +0 bytes
1 -> +32 * 4 bytes
2 -> +64 * 4 bytes
3 -> +96 * 4 bytes
...

Coalesced case:

__global__ void my_kernel(float* x) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  x[i] += 1;
}
0 -> +0 bytes
1 -> +4 bytes
2 -> +8 bytes
3 -> +12 bytes
...
31 -> +124 bytes

All threads in a warp can access 1 FP32 each in one load!

How do GPUs organise kernels?

Streams

Launch GPU operations concurrently:

cudaMemcpy(..., stream1);
axpy<<<n_blocks, threads_per_block, 0, stream1>>>(d_out, d_x, d_y, a, n);

cudaMemcpy(..., stream2);
axpy<<<n_blocks, threads_per_block, 0, stream2>>>(d_out, d_x, d_y, a, n);
  • Increase occupancy
  • Overlap data transfers & comms

Shared memory & __syncthreads()

__global__ void axpy(float *out, const float *x, const float *y, float a, int n) {
  int tid = threadIdx.x;
  int gtid = blockIdx.x * blockDim.x + threadIdx.x;

  __shared__ int sdata[THREADS_PER_BLOCK];

  // Load data from global to shared memory
  if(gtid < n) sdata[tid] = y[gtid];
  __syncthreads(); // all threads in *block* must reach here

  // Do something with shared memory
  if(gtid < n) sdata[tid] += a*x[gtid];
  __syncthreads();

  // Store result back to global memory
  if(gtid < n) out[gtid] = sdata[tid];
}

Note: __syncthreads() operates on block level, not warp level.

We can get shared memory in OpenMP with team-private arrays (see exercise tomorrow).

Beware bank conflicts (not covered here).

Performance recommendations

  • Set block_size to a multiple of 32 to fit warps
  • Track occupancy
  • Avoid data transfers (& use thrust)
  • Avoid branching
  • Ensure coalesced memory accesses
